Add a GitHub Actions deployment workflow to the Troupe project that handles 
database migrations before deploying to Cloud Run.

## File to create
.github/workflows/deploy.yml

## Workflow Requirements

### Triggers
- Run on every push to main branch only
- Do not trigger on pull requests

### Jobs
The workflow must have two sequential jobs:

#### Job 1: migrate
- Runs on ubuntu-latest
- Sets up pnpm
- Installs only server dependencies (pnpm --filter server install)
- Authenticates to GCP using google-github-actions/auth@v2
- Connects to Cloud SQL via the Cloud SQL Auth Proxy before running migrations
- Runs pnpm --filter server migrate
- If this job fails, the deploy job must not run

#### Job 2: deploy
- Runs on ubuntu-latest
- Must declare `needs: migrate` so it only runs if migrations succeed
- Authenticates to GCP using google-github-actions/auth@v2
- Deploys to Cloud Run using google-github-actions/deploy-cloudrun@v2 with:
  - service: troupe-api
  - region: us-central1
  - No manual image build needed — Cloud Run pulls from the connected GitHub repo

### GitHub Secrets required
The workflow must reference these secrets (do not hardcode values):
- GCP_SA_KEY — GCP service account JSON with Cloud Run and Cloud SQL permissions
- DATABASE_URL — Cloud SQL connection string via Auth Proxy socket
- GCP_PROJECT_ID — GCP project ID

3. How the deploy pipeline works:
   - Explain the migrate → deploy sequence
   - Explain that a failed migration blocks the deploy
   - Explain how to roll back a migration manually if needed

4. Multi-phase migration strategy:
   Document this convention clearly with an example:

   When making breaking schema changes (renaming or dropping a column), 
   never do it in a single migration. Always use three separate PRs:

   PR 1 — Add: add the new column alongside the old one
   CREATE TABLE ... ADD COLUMN new_col TEXT;

   PR 2 — Migrate: update all code to use the new column, 
   backfill data if needed
   UPDATE users SET new_col = old_col WHERE new_col IS NULL;

   PR 3 — Cleanup: drop the old column once PR 2 is stable in production
   ALTER TABLE users DROP COLUMN old_col;

   Reason: eliminates the risk window where deployed code references 
   a column that no longer exists.

## CLAUDE.md
Add a new "Deployment" section to CLAUDE.md:

### Deployment
- CI/CD: GitHub Actions → Cloud Run via native GitHub integration
- Two jobs: migrate (runs first) → deploy (runs only if migrate succeeds)
- Never merge to main with a migration you cannot roll back cleanly
- Breaking schema changes (rename/drop) always use the three-phase approach:
  Phase 1 PR: add new column
  Phase 2 PR: update code and backfill data
  Phase 3 PR: drop old column
- Secrets live in GitHub repository secrets and GCP Secret Manager — never in code
- To manually trigger a migration rollback: pnpm --filter server migrate:down

## Constraints

- The workflow file must include comments explaining the migrate → deploy
